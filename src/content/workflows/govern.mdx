Two of these are worth sitting with longer than a table row allows:

<Example id="air-canada-chatbot">
  A customer asked Air Canada's chatbot about bereavement fares. The chatbot invented a policy that didn't exist and told the customer it was real. Air Canada argued in tribunal that the chatbot was effectively a separate entity, responsible for its own statements. The tribunal disagreed. The airline was held liable for what its own agent said.
</Example>

<Example id="meta-hud-bias">
  Nobody instructed Meta's ad-delivery model to discriminate. It learned the pattern from training data, nursing ads skewing toward women, janitorial ads skewing toward men of color, and repeated it at scale, invisibly, until a HUD lawsuit made it visible. A fairness check run on every output before delivery, not sampled after the fact, is specifically designed to catch exactly this: a pattern nobody wrote down anywhere, reproduced faithfully by a system that has no concept of having done anything wrong.
</Example>

</Section>

<Section index="02" kicker="Before it's needed, not after" title="Kill-switch design">

A kill switch designed after an incident is a postmortem action item. Designed in advance, it's four decisions made calmly, before anyone needs them under pressure:

<Figure
  d="D82"
  caption="Kill-switch design — four decisions, made before an incident, not during one."
  alt="Four dimensions of kill-switch design: Triggers (unverified claim detected, spend exceeds guardrail, sentiment drops more than 15%, regulatory notice, data breach), Halt scope (single-agent pause, workflow halt, full system suspension, channel-specific or audience-specific freeze), Authority (marketing lead pauses one zone, CMO halts the full system, legal owns regulatory halts, some triggers auto-fire on threshold breach), Recovery (find root cause, remediate outputs, patch the policy layer, update the audit trail, restart only after the fix is verified)."
>
  <FlowChain nodes={['Triggers — what fires it', 'Halt scope — what it cuts off', 'Authority — who can pull it', 'Recovery — root cause to restart']} />
</Figure>

<Example id="spotify-ai-dj-trust">
  Spotify's AI DJ generates spoken commentary between songs, and early versions referenced a listener's inferred location and current activity. "I see you are at the gym" tested well in a demo and unsettling in practice. Personalization had crossed from delightful to surveilled. The fix capped what the system could reference at all rather than adding a bigger disclaimer: mood stays in, inferred location comes out, with skip-rate monitored in real time as an early-warning signal. AI DJ has run at over 70% positive sentiment ever since the change. Governance prevented the problem here. It didn't clean up after it.
</Example>

<Section index="03" kicker="What regulators are actually asking" title="Regulation">

Every major regulatory framework touching this system reduces to a version of the same demand. Prove it.

<ComparisonTable
  caption="What four major regulatory frameworks require."
  columns={['Core requirement']}

    { label: 'FTC', cells: ['Every claim needs substantiation; AI endorsements need disclosure; biased targeting is an unfair practice'] },
    { label: 'GDPR', cells: ['Consent verified per action; users can demand an explanation; audit trail is a legal obligation'] },
    { label: 'CCPA / CPRA', cells: ['Opt-out signals must reach AI decisions; sensitive data needs explicit consent; annual audits required'] },
  ]}
/>

None of these four frameworks ask for a different governance architecture than the one this chapter already described — a policy layer upstream of execution, claims verified before delivery, a complete audit trail, and a kill switch with defined authority. They ask for the same system. Provably running.

That sentence is the four elements continuous governance operations actually run on, named directly: Policy (checks upstream of execution, not a review after the fact), Claims (verified against an approved list before anything ships), Audit trail (every decision logged, not just the exceptions), and Escalation (the kill switch above, with defined authority to pull it). Six risks, one architecture, four operations running on every decision rather than sampled after some of them.

<Section index="05" kicker="What the job becomes" title="Ten roles, five skills, one translation">

Course material names ten marketing roles that didn't exist five years ago. Three carry the shape of the shift for anyone reading this handbook specifically:

<DefinitionList
  items={[
    { term: 'Marketing AI Architect', body: 'Owns the system this handbook describes, not a single campaign — which workflow gets autonomy, where the policy stack sits, what Shared Memory tracks.     { term: 'Brand DNA Engineer', body: "Owns the machine-readable version of brand voice — Design's content blocks and governance zones, kept current as the single source every generative system checks against, not a guidelines PDF revisited once a year." },
    { term: 'AEO Lead', body: "Owns visibility inside an answer engine's citation, not a rank on a results page — Attract's citation signals, measured by whether an AI overview quotes the brand, not by where a link sits." },

/>

The other seven follow the same pattern: each takes a task this handbook already assigned to a workflow — Sense, Focus, Orchestrate, Govern — and turns it into a named job description. What holds across all ten, named or not, are five durable skills none of them get to skip:

<DefinitionList
  items={[
    { term: 'Systems thinking', body: 'Seeing the loop, not the campaign — the same shift Orchestrate and Execute and Learn both argue for from opposite ends.' },
    { term: 'Brand DNA codification', body: "Turning a brand's identity into something a machine can actually check an output against, not a slide deck nobody opens." },
    { term: 'Causal reasoning', body: 'iROAS thinking: knowing the difference between what a dashboard reports and what a holdout group proves.' },
    { term: 'Agent design', body: 'Writing the policy stack, the guardrails, the kill-switch triggers — the actual decisions this chapter has been describing.' },
    { term: 'The So-What', body: "The one the other four don't replace." },
  ]}
/>

Every workflow on this site eventually produces a number, a segment, a signal. None of it ships on its own — someone still has to say what it actually means to the person receiving it, why a message reads as authentic instead of algorithmic, which cultural moment makes an insight true this quarter and false the next. Course material calls that translation step the So-What. It's the same idea this handbook has taught since [the Insight Gap](/spine/insight-gap) — Signal, Interpretation, Insight, Action — under a name built for saying out loud in a room: given everything the system just found, so what?

</Section>

<Section index="06" kicker="Where the line actually sits" title="Where AI leads, and the close">

Five things stay outside what any of this automates, however good the models get: framing the right question in the first place, bearing responsibility when a decision is wrong, translating a finding into something that means something to a person, anchoring a message in the culture it has to land in, and reasoning across domains no training set ever connected. All five are the So-What, applied at a different point in the loop.
