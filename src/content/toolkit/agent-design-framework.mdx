<Section index="01" kicker="The blank passes, not the walkthrough" title="What it's for">

[The Four-Pass Decomposition Method](/workflows/build/deep-dive/four-pass-decomposition) is the site's most technical page, and it earns that depth running the method against Focus: 12 agents, 5 sub-workflows, 27 tasks. This page doesn't repeat that walkthrough. It's the blank version of the same four passes, Workflow → Sub-workflows → Tasks → Agents → Connections, built to run against a workflow of your own, not Focus's.

<Callout kind="note" title="Read the method first">
Pass 2 before Pass 3 is the one discipline that page insists on: name what needs doing before deciding who does it. This template enforces the same order. Skipping straight to "which agent handles this" is the most common way this framework gets misused.
</Callout>

</Section>

<Section index="02" kicker="Before the first agent prompt" title="When to use it">

Fill this out before writing a single agent prompt or system message. That's the point where a workflow exists as an idea, not yet as anything buildable.

- Scoping a new AI-driven workflow from scratch, before any tool, model, or vendor decision gets made.
- Auditing an existing agent setup that grew ad hoc, to check whether its task boundaries and connections were ever actually decided or just accreted.

</Section>

<Section index="03" kicker="Run against a review-request flow" title="Worked example">

A smaller, deliberately different workflow than Focus's: a post-purchase review-request flow. Running all four passes against it end to end:

<StepList
  steps={[
    { title: 'Pass 1 — Sub-workflows', body: '3 to 6 operational phases.', example: 'Eligibility & Timing → Ask Generation & Send → Response Handling.' },
    { title: 'Pass 2 — Tasks', body: '3 to 8 atomic, platform-agnostic tasks per sub-workflow.', example: 'Eligibility: confirm delivery, confirm no open return, confirm no negative support ticket in 14 days.' },
    { title: 'Pass 3 — Agents (+ what it must NOT do)', body: "Map tasks to agents; set autonomy per the Economics of Error; name each agent's forbidden action.", example: 'Eligibility Checker (L4) — must not override a support-ticket flag. Ask Composer (L3) — must not reference order value. Escalation Router (L2) — must not auto-respond to a detected complaint.' },
    { title: 'Pass 4 — Connections', body: 'Every link, within and across sub-workflows, to Shared Memory, and to governance agents.', example: 'Eligibility Checker writes an object Ask Composer reads; Escalation Router writes to a human queue and to the Learning object.' },
  ]}
/>

Three agents, one sub-workflow shorter than Focus's. But the count isn't the point. Run Pass 1 through Pass 4 in order against your own workflow's actual jobs. That's the discipline the deep-dive names as universal.

<Section index="06" kicker="The row most specs skip" title="Design decision">

Pass 3 above carries a field the deep-dive's own worked table doesn't show: what the agent must *not* do, named alongside what it's responsible for. Most agent specs only state scope in the positive. Inputs, outputs, the job. The forbidden action bounds an agent's autonomy, because the failure mode that gets an organization in trouble is almost never "the agent didn't do its job." It's the agent doing something adjacent to its job that nobody explicitly ruled out, because nobody wrote it down as off-limits in the first place.

</Section>
