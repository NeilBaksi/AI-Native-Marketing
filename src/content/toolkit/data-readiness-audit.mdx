<Section index="01" kicker="An audit, not a scorecard" title="What it's for">

[Shared Memory](/spine/shared-memory) names the schema every workflow reads and writes: identity, state, decision, content, and learning objects. That chapter doesn't ask whether your organization's actual data can populate them — it assumes the objects exist. This audit is the question it skips: for each of the five object types, does the data you actually have support it, or does the object exist only on a slide?

<Callout kind="caution" title="An audit, not a scorecard">
The point isn't a pass/fail grade across every field. Some gaps are launch-blocking; some are cosmetic imperfections nobody should lose a week fixing. The worked example below draws that line explicitly, on purpose.
</Callout>

</Section>

<Section index="02" kicker="Before the build starts" title="When to use it">

Run this before committing to build any workflow, agent, or automation that assumes Shared Memory objects already exist and are trustworthy — not after the build starts and the gaps surface as production bugs.

- Early in an I-MOS adoption effort, right after the [maturity-model](/foundations/maturity-model) self-diagnostic places you at a stage.
- Before scaling autonomy on any workflow — an agent making Fully Autonomous decisions on a Propensity Score built from stale, fragmented identity data is a governance failure waiting to happen, not a data-quality footnote.
- When a workflow's outputs look wrong and the suspicion is the object it read, not the logic that read it.

</Section>

<Example id="ab-inbev-three-consumers">
  The Identity gap above is the same failure at a much larger scale: a single AB InBev consumer, buying across three of the company's own brands, was invisible as one person to three separate campaign systems — not because any model was wrong, but because no Identity object existed anywhere for that consumer to be recognized as one.
</Example>

Three of the five — Identity, Decision, Learning — are launch-blocking here: without them, autonomy can't scale past a demo, because there's nowhere for the loop to write its results. State and Content are real gaps but not blocking; a workflow can launch with 24-hour-stale state and whole-asset content, and tighten both later.

<Section index="06" kicker="Not every gap is a blocker" title="Design decision">

The verdict column forces a real distinction most data audits skip: not every imperfection is a blocker. A field that's slightly stale, or a category share that's off by a rounding error, doesn't deserve the same response as an object that structurally doesn't exist anywhere. Treating every gap as equally urgent trains a team to either ignore the audit entirely or stall a launch over something that was never going to matter — this audit asks the launch-blocking question explicitly, row by row, instead of producing one undifferentiated list of problems.

</Section>
