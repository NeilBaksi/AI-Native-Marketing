This page is a straight account of how the handbook got made. It covers what it was built from, what tools wrote it, and what stops it from being wrong. If a "how the sausage is made" page reads like marketing copy, something's gone wrong with it; this one doesn't try to sell you on the process, just describe it.

## From course material to handbook

The source material is Prof. Sawhney's MKTG 468 course notes. It comprises eleven session decks, eight readings plus a teaching case, a capstone project report, and a sequence of applied case drafts. None of that went straight onto the site. It first became two structured reports: a concept inventory covering roughly 255 named concepts, ninety diagram candidates, and a recommended ten-stage teaching sequence, and a separate report on the two applied threads (the Auranis case sequence and the Salesforce Agentforce capstone) with every number's source flagged.

The fifty-seven pages here were written against those two reports, not against the raw session decks. That's a deliberate layer: it's easier to keep 57 pages of original prose honest against a structured inventory that already separates concept from case from statistic than against eleven decks of raw slide text.

## Why the stack changed partway through

The site started on Astro, chosen for its zero-JS-by-default pages, a reasonable choice for a public teaching site where every kilobyte matters. After the first working pages went up, the actual feedback was about spacing, color, type, and prose reading as a wall of text, not load time. The stated priority was explicit: this is mostly for the author and people he shares it with, load time matters more than payload size, and a loading skeleton is an acceptable answer if a page takes a moment.

That changed the calculus. The constraint Astro's architecture optimized for, near-zero JavaScript, wasn't the actual constraint here, and two other sites in the same portfolio already had a proven, working component vocabulary (diagrams, accordions, tabs, page transitions) built on Vite, React, and Tailwind. Rebuilding a third, different architecture for a third site has a real ongoing cost, since every future editing session has to relearn which pattern applies to which repo. The site was rebuilt on that shared stack partway through, trading zero-JS-by-default for a richer, already-proven component vocabulary. That trade came with real costs, accepted rather than hidden:

- A heavier JavaScript baseline than a zero-JS site would ship.
- A weaker Content Security Policy — framer-motion writes inline styles at runtime, which forces `style-src 'unsafe-inline'`; there's no way to keep the animation library and avoid it.
- Hash-routed URLs (`/#/foundations/the-problem`) instead of clean paths, since GitHub Pages has no server-side rewrite rule for a single-page app.

## Keeping facts honest

Course material, real-company facts, and fabricated data all sit next to each other in this handbook, and mixing them up would be the single worst failure mode for a teaching site. Every fact used on the site — a statistic, a real-company example, a case number — carries one of three provenance classes, visually distinguished wherever it appears:

<DefinitionList items={[
  { term: 'Verified public fact', body: 'A real company, a real number, backed by a citable public source, a filing, a press release, reputable press.' },
  { term: 'Course-sourced claim', body: "A statistic or claim from the course material that couldn't be independently verified against a public source. Marked as course-sourced, with the year, so its status is visible." },
  { term: 'Synthetic or illustrative data', body: 'Fabricated numbers used for teaching. The Auranis case company is fictional, and the Salesforce Agentforce capstone uses a synthetic dataset layered onto a real company name. Every figure built on this carries a persistent, hard-to-miss synthetic-data banner.' },
]} />

That's not a style guideline that relies on someone remembering to apply it — it's checked mechanically. Facts live in a typed registry, not hard-coded in page prose, and an incomplete provenance record fails to compile. A separate script runs at the end of every build and fails it, rather than warning, if: a page in the site's manifest has no matching content file (or vice versa); an internal link points at a page that doesn't exist; a page uses a fact id that isn't registered; a page uses a synthetic fact without declaring itself synthetic at the page level; a live page still has an unfinished-content marker in it; or a page uses a component tag that isn't actually registered anywhere. <Mark>It's a build gate. The build fails if any of that is wrong.</Mark>

The same script also enforces a chunking rule: no more than two bare paragraphs in a row without a diagram, callout, example, table, or quote breaking them up. That rule exists for a reader's sake, not a machine's, and it's checked the same mechanical way as everything above it, on every page, every build.

## If something's wrong

This repository is public. If you find an error — a broken link, a misattributed claim, a fact that's aged out of date — the fastest way to flag it is an issue on the [GitHub repository](https://github.com/NeilBaksi/AI-Native-Marketing) or a direct message to the author. There isn't a formal review process for outside contributions set up yet, so treat an issue as the reliable path for now rather than assuming a pull request will be picked up.
